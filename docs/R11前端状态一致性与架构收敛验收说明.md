## 4. 修复方案与保留边界

`upload-draft`提供`recoveryReady`与`requireRecovery()`，SSR和客户端初值一致为false；读取校验成功后才放行。失败不自动过滤/写回未知原记录，不输出记录内容。

识别Composable在上传、任务POST和新key生成前检查；putReceipt再次守卫，防止仅禁用按钮而其他调用方绕过。上传/任务页只增加既有disabled条件，复用错误区域，不改视觉。

正常记录继续按确认账号过滤/退出清理；损坏、不可读的未知记录不自动抹掉。需要先核对已有任务，再修复会话存储和重新加载。没有“清除后盲目重提”的捷径，没有跨标签页或关闭标签页恢复的新功能。

R12a先画出API→对象存储→队列→识别的资源路径，测合成图片解码峰值、连接和全局/账号并发，再定义原子预留/释放与明确拒绝码。区分已有单文件10MB/20M像素与累计容量。资源/额度事务或Schema调整必须单独评审；4核4GB承载量应靠测试，不凭规格保证。

具体起点：`server/services/image-upload.ts`在创建/重试文件记录前调用normalizeImage；`services/recognition/app/main.py:23/68`有Python进程内推理Lock，但读取图片发生在取得锁之前。该锁不等于Nuxt上传解码、整个请求或多进程的全局资源限制，应分别测量，不能因已存在锁就宣布并发资源治理完成。

新增维护成本只有三个纯函数和明确恢复状态。Fail-Closed会暂时阻止存储损坏用户提交，这是避免未知结果重复提交的取舍，不能声称所有恢复体验已完善。
