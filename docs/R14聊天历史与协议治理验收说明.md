# R14 聊天历史、调用审计与快照协议治理

日期：2026-10-28。基线：R13 `c13630d6fe9b3813e51dc54c328029fc8b3ead74`；分支：`refactor/r14-chat-protocol`。Schema、事务及兼容协议已获用户批准。没有生产迁移、真实对象清理、付费模型调用或原始历史推送。

## 1. 轮次与 Prompt

保留原有 ChatTurn 状态、消息、失败片段和停止记录。停止仍为现有 FAILED 业务终态，不新增业务状态。

原规则按 ChatMessage.status=COMPLETED 取最后 19 条，导致失败/停止的 USER 问题进入下一次请求；裁剪也不能证明完整问答。新规则在 `chat-history.ts` 选择有 COMPLETED 轮次证明的 USER，按持锁分配的 position 排序，再验证同账号、同会话、同 turn 的完整成功 USER/ASSISTANT 配对及相邻位置。时间或随机 UUID 不再决定 Prompt 顺序。

只使用最近至多 9 对成功问答，当前问题单独追加一次；20,000 字符预算按整对从旧到新淘汰，当前问题保留。它是字符预算，不宣称精确 token 限制。无法可靠配对的 turnId=null 旧记录、破损配对、失败和停止整轮只展示，不进入模型。AccountChat 增加简短说明，没有重做 UI。

例：成功 Q1/A1 → 失败 Q2/部分 A2 → 新问题 Q3，实际请求为 Q1/A1/Q3；停止 Q2 同理。重试同一个 Q3 时，不将上一次 attempt 的片段加入上下文。绑定的 FormulaVersion.id/LaTeX 保持不变，不用最新编辑内容替换。

## 2. Schema 与迁移

具体字段、枚举与审批边界见《R14实施前审查与Schema审批方案.md》；实际定义以 `prisma/schema.prisma` 和 `prisma/migrations/20261028000000_chat_revision_calls/migration.sql` 为准。

- Conversation 新增 `revision BigInt @default(0)`、非负 CHECK，无额外重复索引。历史行从 0 开始，不补造历史修订。
- 新增 ChatCallAttempt、ChatCallStatus、ChatUsageSource。复合外键 `[turnId,ownerId]` 复用 ChatTurn 唯一键；唯一键 `[turnId,workerAttempt,callIndex]`；账号/创建时间索引、状态/更新时间索引。
- queueJobId 是审计标识，没有指向队列可归档记录的级联外键；审计随所属轮次/账号删除，不充当永久财务账本。
- SQL CHECK 约束尝试次数、非负时长/token、HTTP 状态范围、提交/丢弃互斥，以及 UNKNOWN/MOCK 不得填充虚假 token 用量。
- 迁移是加法变更，使用 BEGIN/COMMIT；没有删除历史消息、重建业务表、改每日额度或 R12 资源数据。

只在新建 R1 环境 `54098baa-3f07-48a2-b33d-ca5aab9bb523` 实际执行。故障注入另外在该数据库的随机独立 schema 中执行迁移主体，验证旧行 revision=0，并在 DDL 后注入错误，ROLLBACK 后该 schema 不存在。它验证 SQL 事务回滚，不冒充 Prisma migration engine 进程崩溃测试。

## 3. 修订号事务覆盖

| 可见变化                | 实现入口                                   | 同事务保护                                                |
| ----------------------- | ------------------------------------------ | --------------------------------------------------------- |
| 提交用户问题/新轮次     | conversations.submitChatTurn               | 会话锁、幂等键、额度/入队、revision                       |
| 开始新 Worker attempt   | worker/lifecycle.beginAttempt（chat 分支） | 会话 → 真实 queue claim → turn/revision                   |
| 清空旧片段/设置模型来源 | worker/chat 初始化                         | 同上，并创建调用审计                                      |
| 流式片段                | chat-progress.saveChatProgress             | 同上；相同内容不重复递增                                  |
| 正常完成                | worker/chat 完成事务                       | assistant、turn、revision、调用提交标记、队列确认共同提交 |
| 失败/重新排队           | task-lifecycle.transitionFailure           | 复用 R13 围栏/失败消息，递增 revision                     |
| 用户停止                | chat-progress.cancelChatTurn               | 队列取消、失败消息、turn、revision 原子；重复停止不变     |
| 后台恢复/GET兼容核对    | task-reconciliation                        | 复用 R13 真实队列事实、会话锁和 revision                  |
| 可变公式标题            | SQL 标题触发器                             | 标题修改同事务更新其关联会话 revision                     |

`chat-revision.ts` 仅负责小型修订操作，不替代 R13 执行权规则。失效 claim/旧 attempt 仍不能提交答案或片段。修订号不能用于认定模型计费或取得执行权。

GET、SSE 完整读取和停止后的读取，均在 RepeatableRead 事务内构造 DTO，包括会话、消息、当前 turn、公式上下文。隔离测试暂停第一次会话读取，另一连接提交新片段，再继续读取，所得 DTO 仍是同一旧 revision/旧片段；下一次读取才得到新修订。

公式标题 AFTER UPDATE 触发器只在标题变化时运行；先按 conversation.id 顺序锁关联会话，再递增 revision，不取得 queue/turn 锁。Worker 不反向取得 Formula 行锁。新会话创建另在 Serializable 事务中取得 Formula FOR SHARE 锁，并在数据库序列化冲突时至多重试3次；没有外部调用或额度副作用。强制暂停新会话插入、确认改名实际等待行锁，再释放创建事务，验证 SSI 冲突重试后触发器覆盖新会话，避免遗漏 phantom。60 个关联会话、两个 Serializable 保存窗口的专项测试只有一个成功，另一个按 R6.1 返回 VERSION_CONFLICT；每个快照的标题/修订同步，固定版本不变。另外验证实际 Worker 片段写入与改名竞争、失败事务 revision 整体回滚。

60 会话测试记录的是竞争保存加完整读取核验总耗时，不能当成纯触发器延迟或生产承载保证。更大扇出和 Linux 多实例压测仍归 R17。

## 4. 请求、Worker 和供应商调用

```text
ChatTurn/requestKey：一次业务提交、一次额度预留
  ├─ Worker attempt 1（pg-boss retryCount + 1）
  │    └─ ChatCallAttempt(callIndex=1)
  └─ Worker attempt 2（同一个业务任务，不再扣额度）
       └─ 独立 ChatCallAttempt(callIndex=1)
```

LangChain 与 SDK maxRetries 继续为 0，没有新增库内自动重试。

调用记录在有效 claim 的初始化事务中准备；供应商 fetch 前持久化 dispatchIntentAt，写库失败不发起请求。fetch 包装器观测 transportInvokedAt、HTTP 响应时间、状态和经过白名单过滤的 x-request-id。观测失败会取消该网络操作，并已为 promise 注册错误处理。

网络与数据库没有共同事务：意图不代表已发送；崩溃后无法证明供应商未调用或未计费。后台按真实 queue/claim 将失活遗留记录归 UNKNOWN；不会退款、重新调模型、释放文件或改任务终态。启用 R13 后台核对时，该扫描独立于活动 ChatTurn，使用有界 keyset 批次，终态轮次的遗留调用也可被发现。

状态表示本地观察：FAILED 是本地流/调用失败，不保证供应商未计费；CANCELLED 是已确认用户停止的本地调用；SUCCEEDED 表示完整流已收到，不等于答案已持久化。`resultCommittedAt` 才与业务完成及队列确认同事务提交；失去执行权的结果不能写业务数据。迟到错误补写带 `resultCommittedAt=null` 条件，提交成功后响应丢失不会把成功审计改成失败。

仅从供应商原始 usage 取已报告的非负整数，记录来源 PROVIDER_REPORTED；缺失为 UNKNOWN/null，Mock 为 MOCK/null。不推算缺失总数、不存虚假费用、不存 Prompt/消息正文/密钥/完整原始错误。durationMs 是本机观测区间，不是精确供应商计算时间。历史任务不回填假审计。

## 5. v2 快照和旧客户端

SavedConversation 增量增加 `protocolVersion:2`、`revision:十进制字符串`。不直接序列化 BigInt，不使用客户端时间排序。浏览器按十进制串长度和字典序无损比较，也覆盖超过 JS 安全整数范围的修订号，不引入 BigInt 字面量的旧构建目标问题。

- GET、SSE、停止响应使用同一完整快照规则；首次创建会话响应也包含新增字段。
- 消息提交仍保持原来的 **202 + TaskState**，没有擅自改成完整快照；随后 GET/SSE 获取权威会话。
- 新客户端 GET/停止声明 X-Conversation-Protocol:2，EventSource 使用 `?protocol=2`。
- 先检查账号/会话/连接归属，再检查 revision：旧修订丢弃；同修订同内容不更新；同修订不同内容报协议冲突、进入完整重读；新修订允许合法 retry 清空。
- 保留固定公式与不可变消息校验。缺失/非法修订号不静默降级接受旧状态。
- 旧客户端仍获得完整 snapshot 事件及旧字段，新增字段可忽略。旧客户端不能被宣称具有 v2 同轮排序保证。
- 重连总是先读最新完整快照；不依赖事件日志，不补交消息、不启动新模型任务。

R11 的账号/请求代际、卸载取消和旧 EventSource 实例检查保留。相同 revision 冲突与所有关键 GET/SSE/停止排列均有纯客户端测试；真实 HTTP 覆盖鉴权、两种 SSE、停止、重连、18 秒无变化心跳和不重复建任务。

## 6. SSE 成本与真实测量

保留完整快照。首次完整读取；后续先读轻量 revision，未变复用已验证 DTO，变化时再进入一致性完整读取。v2 每 6 tick 心跳，正常情况下约 4.5 秒（数据库/调度延迟另计）；客户端 watchdog 识别心跳。v1 每 12 tick 补发完整快照，兼容旧 watchdog。保留 R13 核对及身份检查。

测量脚本 `scripts/measure-chat-baseline.ts`，R13 冻结读取逻辑在 `tests/support/chat-baseline.ts`，仅供测量。旧基线脚本也保留在提交 `157f9d8`。同一组 fixtures 比较：0/20/100/200 条历史消息 × 1/4 连接 × 持续更新/等待 × 旧完整读取/一致性完整读取/revision 探测，共 48 组，每组 20 tick。

下表为 100 条历史、4 连接；字节含新协议事件 id，不含 HTTP 头和压缩。

| 场景       | 方式           | 实际读取SQL总数 | 每tick P50/P95 ms | 快照帧字节 |
| ---------- | -------------- | --------------- | ----------------- | ---------- |
| 持续更新   | 冻结R13读取    | 400             | 17.99 / 21.69     | 9,225,360  |
| 持续更新   | 一致性完整读取 | 480             | 22.03 / 32.65     | 9,228,808  |
| 持续更新   | revision探测   | 556             | 23.54 / 29.19     | 9,228,960  |
| 无变化等待 | 冻结R13读取    | 400             | 16.94 / 22.59     | 463,700    |
| 无变化等待 | 一致性完整读取 | 480             | 22.84 / 34.36     | 463,880    |
| 无变化等待 | revision探测   | 100             | 4.48 / 11.51      | 463,880    |

结论有明确边界：无变化读取 SQL 较旧方案减少 75%；持续更新增加探测及一致性事务开销，SQL 增加 39%，传输字节基本不降。没有宣称所有场景提速，也没有实施缺少事件重放依据的增量补丁。后续性能治理可研究自适应探测或有可靠恢复的增量，但不能牺牲一致性。

计数来自实际 Prisma query 事件，字节按实际 snapshot 帧格式编码。只计读取与快照帧；不按 750ms 实时 pacing，不含认证、后台核对、心跳、v1周期补发、代理压缩和网络开销，因此不能当作完整服务压测。冻结 R13 逻辑运行于当前测试 Schema；先前旧 Schema 真实基线也得到每完整读取 5 条 SQL，与本次基线相符。全量数字及源码哈希在本机 `tmp/r14-comparison-report.json`，不上传运行清单或凭据。

## 9. 未运行及剩余风险

- 没有真实 DeepSeek 计费、供应商生产网络故障、Linux信号/多机压测或全站R3—R10重新视觉验收。
- 最近100条消息及hasEarlierMessages限制保持，尚无“加载更早”端点；UI不能宣称展示完整无限历史。
- 不保证供应商恰好一次计费；崩溃重试可能再次调用。业务额度仍只计一次，审计明确未知边界。
- revision覆盖依赖所有写入者升级；旧Worker混跑会破坏保证，不能仅更新前端。
- 标题关联规模显著大于60时的锁等待需R17压测；当前专项没有发现反向锁或Serializable保护退化。
- 持续生成仍发送完整快照，成本未全面降低；不承诺生产并发容量。
- 断网/乱序由HTTP与客户端纯函数分层验证，没有穷举所有浏览器、代理和操作系统网络组合；保留只读恢复。
- 新调用审计有长期存储增长；后续应按账号隐私策略和诊断窗口设计归档，R14没有自动删除审计。
