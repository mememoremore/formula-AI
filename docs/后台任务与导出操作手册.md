# 后台任务与导出操作手册

## 本机启动

数据库与存储沿用前面的配置，不需要重新生成密码或重建数据卷。

```powershell
npm run db:up
npm run db:migrate
npm run storage:up
npm run worker:setup
```

然后分别在两个终端启动：

```powershell
# 终端一
npm run dev

# 终端二
npm run worker
```

打开 `http://127.0.0.1:3000`。只启动 Nuxt 也能提交并保存任务，但需要 Worker 才会处理。浏览器刷新不取消任务。

`worker:setup` 安装或升级固定版本的 pg-boss 专用结构，并创建识别、对话、导出三个队列。可以重复运行；业务迁移仍由 Prisma 管理。不要手工修改 pg-boss 表结构，也不要把它混入应用的 Prisma schema。

## 怎么体验

1. 创建账号，上传图片。页面先进入识别任务，完成后自动进入公式详情。
2. 在详情选择“AI 解析这个版本”，创建账号对话并发送提问；从底部 AI 栏或账号空间可回到“我的对话”。
3. 在详情的“导出可编辑 Word”选择版本，提交后等待完成，再下载文档。
4. 修改公式后，可选择旧版本再次导出，核对两个文件的内容和版本号。

识别和回答仍是固定模拟内容，页面有明确说明。Word 文件是真实 DOCX，公式是可编辑的原生对象。

## 每日额度配置

服务端可设置：

```dotenv
NUXT_RECOGNITION_DAILY_LIMIT=50
NUXT_CHAT_DAILY_LIMIT=30
NUXT_EXPORT_DAILY_LIMIT=20
```

有效额度为1～10000的整数，修改后重启 Nuxt。按 UTC 日重置，北京时间为08:00。自动重试不会再扣额，失败任务仍占已接受请求的一次额度。清空浏览器数据不会重置账号额度。

## Pandoc 配置

本机已经下载并验证官方 Pandoc 3.12.1，位于：

```text
.tools/pandoc-3.12.1/pandoc-3.12.1/pandoc.exe
```

`.tools` 不纳入源码版本管理。其他机器需安装 Pandoc，或在 Worker 环境设置绝对路径：

```dotenv
PANDOC_PATH=C:/工具/pandoc/pandoc.exe
```

该路径只供服务端执行程序使用，不传给浏览器。非 Windows 环境可使用 PATH 中的 `pandoc`。版本升级后重跑文档样例与真实 Word/WPS 验收，不能只检查退出码。

发布到服务器时，应同时准备 Nuxt、Worker 所需源码/运行依赖、Prisma Client 和 Pandoc；单独复制 `.output` 不包含独立 Worker 的所有运行文件。当前 Worker 通过 `tsx` 运行，部署打包和进程守护在第14天落实。生产服务需要注入环境变量，不能依赖 Nuxt 自动读取工程 `.env`。

## 常见状态与排查

| 现象                      | 先检查什么                                                  |
| ------------------------- | ----------------------------------------------------------- |
| 提交提示队列未就绪        | PostgreSQL 是否运行，是否执行 `worker:setup`，Nuxt 是否重启 |
| 长时间排队                | Worker 是否运行；终端是否显示三个业务队列已启动             |
| Worker 重启后仍显示处理中 | 等待心跳/执行期限失效及监督恢复；不是立即重新领取           |
| 处理中暂时失败            | 会自动有限重试，最多3次；不要反复点击创建新任务             |
| 任务最终失败              | 阅读页面提示；修正输入或服务配置，再显式重新提交新请求      |
| Word 不支持某个公式       | 检查 LaTeX 语法及命令；本次不接受转换警告后静默降级         |
| Word 转换工具未配置       | 检查 Worker 的 `PANDOC_PATH`、执行权限和 Pandoc 版本        |
| 下载尚未就绪              | 等任务完成；失败任务没有成品下载链接                        |
| 今日次数已用完            | 等下一个 UTC 日，或由管理员修改服务端额度配置               |

正常停止 Worker 使用终端 Ctrl+C；进程异常退出后，数据库任务仍保留。任务默认最多3次尝试，执行期限90秒并启用10秒心跳，监督周期5秒；恢复时间受数据库和进程状态影响。最终失败不会无限自动重试。

## PENDING 文件排查

Worker 在转换成功后会先登记 PENDING 再上传。如果进程直接退出，可能留下未发布的对象。可以用只读 SQL 查找：

```sql
SELECT id, "ownerId", name, status, "createdAt"
FROM stored_files
WHERE kind = 'DOCX' AND status = 'PENDING'
ORDER BY "createdAt";
```

这些文件没有完成任务的下载入口。清理前应确认没有活动任务且没有 ExportTask 引用，核对所属用户、bucket 和 objectKey 后再处理对象与元数据。本次没有自动清理历史文件，没有设置桶公开访问。

## 运行验收

`test:jobs` 会控制任务领取并模拟 Worker 退出，需先停下单独的 Worker，保持 Nuxt、数据库和存储运行：

```powershell
npm run test:jobs
npm run test:documents
```

随后重新启动 `npm run worker`，再运行需要实际消费者的回归：

```powershell
npm run test:workspace
npm run test:library
npm run test:auth
npm run test:db
npm run test:api
npm run typecheck
npm run build
npm run test:private-config
```

测试只创建、清理各自随机临时账号，队列测试结束也清理相应账号的队列记录和私有对象。不在有真实生产流量的环境运行这些开发测试。
