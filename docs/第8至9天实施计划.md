# 第8至9天实施计划

依据：[十五天开发计划](../十五天开发计划.md)及用户确认的 Day8、Day9 范围。当前会话按 brainstorming、writing-plans 和 executing-plans 执行，文档使用中文名称，代码按单一职责组织。

## 设计约定

任务数据、每日额度和 pg-boss 入队通过官方 Prisma 事务适配器共同提交。Nuxt 只负责鉴权和业务 API；独立 Node Worker 负责识别、模拟回答和 Word 转换。现阶段识别与回答仍使用固定模拟适配器，LangChain TS 尚未选定。

识别、对话轮次和导出均使用明确的排队、处理、完成、失败状态；单次任务最多执行3次。业务写入和队列完成在同一事务中校验当前执行权，防止失效 Worker 提交结果。失败重试不重复生成公式、消息或文件。手动重新提交使用新请求键并消耗新请求额度。

每日额度按 UTC 日期分别计算识别50次、对话30轮、导出20次，可通过服务端配置调整。统计的是被接受的任务数，失败任务也占额度，自动重试不重复扣除。数据库原子更新防止多个进程并发绕过限制。

对话绑定服务器查询到的公式版本，客户端不能提供替代 LaTeX 或系统消息。同一对话一次只允许一轮排队/处理；刷新能恢复状态和记录。

导出绑定不可变版本并记录当时标题。使用 Pandoc JSON AST 传入纯文字与 Math 节点，禁止把用户输入当作命令、文件路径或 Markdown/原始 XML。DOCX 必须包含原生 OMML，转换警告或缺失公式均视为失败，不用图片冒充可编辑公式。私有下载检查会话归属。

## 关键代码边界

`server/queue` 管队列和执行权，`server/database` 管任务和额度事务，`server/worker` 管各类处理器，`server/documents` 管转换与文件验证，`shared/types/tasks.ts` 管页面契约。页面轮询封装在组合函数里；任务、对话和导出组件分别负责自己的交互。

本机工具采用项目内便携 Pandoc，不改全局安装。生产环境必须同时启动 Nuxt 和 Worker，并配置 Pandoc；缺少依赖时应明确失败。没有 Git 仓库，不创建提交或工作树。
